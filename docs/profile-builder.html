Profile builder

A deployment profile says what a group of users should end up with — interpreters, named venvs and their packages, repos to clone, an editor, settings — and who gets it. acorn apply reads them; they're idempotent, so the same file is both first provisioning and later drift repair.

Build a folder of them here. One marked default = true reaches everyone; the rest reach exactly the users they list, layered on top.

Who gets what

The rule the folder encodes, resolved for one login name — the same as acorn apply pointed at the folder (profile.distributed_to): the default first, then any opt-in profile that lists this user.

Reference — the keys a profile accepts
KeyMeaning
pythonInterpreters to install (list). Every venv is built from one of these.
[[venv]]name, optional python (base tag like 312), packages, default = true (one max), default_packages = false for a bare venv.
[[repo]]url, and install = a venv name or list ("dev", ["dev[gui]", "ml"]). Omit install to clone only.
editor"vscode" / "spyder", or a list. The bundled editor this deployment installs.
toolsconda-forge command-line tools (list).
[config]Settings apply may write: default_base, default_venv, venv_default_packages, vscode_flavor, extension_gallery, vscode_extensions. Install-time settings stay in global.conf.
[distribution]default = true (everyone) or users = [...] (opt-in) — not both. Neither = applied only by explicit path.

apply never destroys: an existing venv or repo is left as-is. A profile's [[repo]] dependencies are not auto-derived for an offline bundle — list them in the bundle's packages by hand.

Mirrors acorn/profile.py and acorn/bundle.py. When they disagree, the tools are right and this page is stale — see docs/PROFILES.md and tests/test_config_builders.py.
